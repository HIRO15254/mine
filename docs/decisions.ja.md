# 決めたこと

すでに決めたことと、その理由の記録です。変えたいときは、ここを読んでから理由ごと見直し、変えたら追記します。新しいものを下に足します。

| 日付 | 決めたこと | 理由 |
|---|---|---|
| 2026-11-05 | 予定は Google カレンダーを正とし、Mine は読むだけにする | 予定を 2 か所で持つとずれる。編集は Google カレンダーが十分に良い |
| 2026-11-05 | タスクと時間の記録は Mine の D1 に持つ | 3 つの日付や単価など、既存のツールに無い形で持ちたい |
| 2026-11-05 | 利用者は自分だけ。`ALLOWED_EMAILS` で限定する | 個人用のダッシュボードなので、共有や権限の仕組みを持たない |
| 2026-11-06 | 変更は `master` へ直接 push し、PR は作らない | 個人のプロジェクトなので PR の手順は要らない。代わりに push 前と本番デプロイ前に同じ検査を必ず通す |
| 2026-11-06 | デザインは Claude Design のキャンバス「Mine UI」を正とし、コードはそれを写す | 見た目の判断を 1 か所に集め、コードとデザインのずれを差分で追えるようにする |
| 2026-11-06 | デザインシステムを Cryst から分け、Mine Design System にする | アイコンに合わせた見た目にしたい。Cryst の変更は頼んだときだけ取り込む |
| 2026-11-06 | 強調は色ではなく「光」にする（`primary` は暗い画面で白、明るい画面で墨） | アイコンの「黒地に光る白い結晶」に合わせる。色はプロジェクトの 5 色だけに使う |
| 2026-11-06 | Claude の接続は Mine 自身の OAuth サーバーで行い、同意画面は API 側が配信する | cookie が届かないブラウザでも接続できるようにする |
| 2026-11-11 | `/v1` は個人用 API トークンだけ、OAuth のトークンは `/mcp` だけで使える | 同意画面が約束した範囲より広く使えないようにする |
| 2026-11-11 | cookie は `SameSite=None` のままにし、`/trpc` の書き込みは `Origin` で確かめる | Web と API を別サイトに置いても動く形を保ちつつ、別サイトからの書き込みを断る |
| 2026-11-11 | 計測中のタイマーは 1 つだけ。データベースの制約で守る | 同時に 2 つの依頼が来ても 2 つ走らないようにする |
| 2026-11-11 | 時間の記録があるプロジェクトは削除できず、アーカイブする | 削除すると過去の記録からプロジェクトと単価が外れ、集計が変わってしまう |
| 2026-11-11 | 月の繰り返しは、最初の完了のときに日を固定する | 31 日のタスクが 2 月のあと 28 日のままになるのを防ぐ |
| 2026-11-11 | オフラインでは書き込みを溜めず、すぐ失敗させて入力を戻す | あとで送る仕組みは、順番や取り消しの扱いが難しく、気付かない失敗を生む |
| 2026-11-11 | 検査は `bun run verify` の 1 つにまとめ、pre-push と本番デプロイの両方で走らせる | 手元で通ったものだけが本番に出るようにする |
| 2026-11-12 | PR 用の CI とプレビュー環境、テンプレート由来のスクリプトとスキルを消す | PR を使わないので動いたことが無く、保守だけが残っていた |
| 2026-11-12 | README と `docs/` は日本語だけにし、`AGENTS.md` は英語にする | 2 つの言語で持つとずれる。読む人に合わせて 1 つにする |
| 2026-11-12 | UI の文言は、メッセージは丁寧語、ボタンや項目名は短い体言止めにする | アプリの実際の文言に手引きを合わせた |
| 2026-11-12 | 依存関係は月に 1 回、定例の作業で更新する | 自動で PR を作る仕組みは、PR を使わない運用と合わない |
| 2026-11-12 | `ALLOWED_EMAILS` は依頼のたびに確かめる | アカウントを作るときだけ確かめると、一覧から外してもログインやトークンが生き続ける |
| 2026-11-12 | ラベルの名前は大文字と小文字を区別せずに重複を確かめる | `Next` と `next` が別のラベルになると、「次にやる」の印が効かないものができる |
| 2026-11-12 | タスクの手動の並び順（`task.sort_order`）は使うのをやめる | 書く処理が無く、常に 0 で並びに効いていなかった。必要になったら設計して足す。列そのものを消す migration は別に出す |
| 2026-11-12 | 既にある表は、新しい規約（`check()` 制約など）に合わせて作り直さない | 作り直しは表を消して作る操作で、外部キーの連鎖で記録が消える危険がある。規約は新しい列から守る |
| 2026-11-12 | 列を消すときは 2 回に分けて出し、スキーマと migration の一致をテストで確かめる | migration は新しい Worker より先に本番へ入るので、古い Worker がまだ読む列を消すと壊れる |
| 2026-11-12 | カバレッジには部分ごとの下限を置き、下げて通すことはしない | 全体の数字 1 つだと、テストの厚い API が Web の薄さを隠す。下限は現状の少し下に置き、上がったら引き上げる |
| 2026-11-12 | パッケージの境界、MCP ツールの約束、スキーマと migration の一致はテストで守る | 文書に書いた決まりは、守られているか誰も確かめなくなる。破ると `verify` が落ちる形にする |
| 2026-11-12 | ブラウザで通すテスト（`bun run smoke`）は `verify` に入れない | ブラウザの用意が要り、デプロイのたびに走らせると遅く、落ちる理由が増える。起動や依存関係を触ったときに走らせる |
